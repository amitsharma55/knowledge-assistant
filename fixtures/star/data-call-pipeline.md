# Data Call Pipeline

The shared pipeline behind every state regulatory data call. Each state's data
call runs through these same stages; what differs between states is the data
elements collected and the processing rules applied, which live in the
per-state documents.

Nothing in this document is state-specific. If a detail only applies to one
state, it belongs in that state's overview, data elements or processing rules
document instead.

## Extract

Source data is pulled from two systems and landed in **Redshift** first:

- The centralized **Redshift** warehouse holds policy, premium and loss data
  for current and recent terms, already conformed across lines of business.
- The **mainframe** holds historical terms and the legacy coverage detail that
  predates the warehouse. Extracts are taken as fixed-width files, transferred
  nightly, and loaded into Redshift staging tables.

Extracts run against a reporting-period snapshot rather than live tables, so a
data call re-run weeks later produces identical figures. The snapshot is taken
at period close and never updated; a correction requires a new snapshot and a
full re-run, which is deliberate — regulatory submissions must be reproducible.

## Staging

Extracted data is written to S3 as **parquet**, partitioned by data call and
reporting period:

```
s3://sf-star-datacalls/<state>/<reporting-period>/<dataset>/
```

Parquet is used rather than CSV for column pruning: report queries typically
read a handful of columns from wide exposure tables, and the difference is
minutes rather than seconds on a full-year extract. Files are written with
Snappy compression and a target size of 128MB per part.

Staged data is immutable. A re-run writes a new reporting-period prefix rather
than overwriting, so a submitted figure can always be traced back to the exact
files it came from.

## Report execution

Reports are generated by SQL run against the staged parquet, one query per
report. Each state maintains its own report SQL, since both the columns
selected and the aggregation logic are state-specific.

- Queries are held in version control alongside the pipeline, one file per
  report, named for the report it produces
- Each report writes a single output dataset back to S3 under a `reports/`
  prefix
- Validation queries run after the report queries and produce an exceptions
  dataset rather than failing the run, so reviewers see every problem at once
  instead of one per re-run
- A report that produces zero rows is treated as a failure, not an empty
  result: it almost always means an upstream partition was missing

## Publishing

Completed report datasets are published to **QuickSight**, where the reporting
team reviews them before submission:

- One QuickSight dataset per report, refreshed at the end of each run
- A review dashboard per state, showing every report alongside its validation
  exceptions
- Submission files are exported from the reviewed datasets, not regenerated,
  so what is submitted is exactly what was reviewed

## Scheduling and orchestration

- The pipeline is orchestrated by Step Functions, one state machine per data
  call, with extract, stage, report and publish as separate states
- Runs are scheduled monthly during the collection window and on demand outside
  it
- A failed state halts the run rather than continuing; partial report sets are
  never published, because a reviewer cannot tell a missing report from a
  report with no rows
- Run history and per-state timings are on the Star operations dashboard
